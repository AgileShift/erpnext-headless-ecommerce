## 5. Decisiones aceptadas del ecommerce

### Frontend

Conservar:
- Vue 3.
- Pinia.
- Storefront UI.
- La experiencia de catálogo existente.

No migrar a React para aprovechar un SDK.

No reemplazar la biblioteca visual sin una necesidad demostrada.

### ERP

ERPNext es el sistema de referencia para:
- Productos y variantes.
- Listas de precios.
- Descuentos y reglas comerciales.
- Impuestos.
- Monedas y conversiones.
- Existencias y reservas.
- Clientes, contactos y direcciones.
- Cotizaciones.
- Pedidos.
- Facturas.
- Cobros.
- Entregas.
- Documentos y notificaciones comerciales.

El propietario confirmó Frappe/ERPNext v16.50 o superior.
Verificar los números y commits exactos antes de usar APIs específicas.

### Exclusiones

No utilizar:
- Frappe Shop.
- Frappe Webshop.
- Un segundo ERP para gestionar la tienda.
- Un nuevo motor comercial como Medusa o Shopify.
- Una migración a React.
- Google/Facebook OAuth en el lanzamiento.
- WhatsApp/SMS para autenticación en el lanzamiento.
- Compra como invitado.

No crear 1.600 Website Item como requisito para publicar el catálogo.

### Autenticación

Proveedor elegido explícitamente:
Supabase Auth gestionado.

Método elegido:
Código de un solo uso por correo electrónico.

No desarrollar:
- Un motor de contraseñas propio.
- Un generador de OTP propio.
- Un sistema propio de recuperación de contraseñas.
- Un emisor propio de tokens cuando el proveedor ya resuelve esa necesidad.

Supabase gestiona:
- Identidad de autenticación.
- Códigos de acceso.
- Verificación.
- Sesiones y renovación según su SDK y configuración.

Las cuentas de Supabase viven fuera de la base del ERP.

### Separación de usuarios

Los compradores NO deben crearse en el DocType User del ERP.

Esto incluye:
- System User.
- Website User.

No usar el signup nativo del ERP para compradores.
No activar Social Login del ERP para resolver la autenticación de la tienda.
No utilizar funciones de invitación que creen Website User.

El hecho de que una persona sea Customer o Contact no debe convertirla en
usuario del ERP.

### ERP privado

Los compradores no deben acceder a la aplicación del ERP ni depender de su
dominio desde el navegador.

Esto afecta:
- APIs.
- Imágenes.
- Archivos.
- PDFs.
- Historial.
- Enlaces en correos.
- Retornos de pago.
- Callbacks del proveedor.

Ocultar enlaces o configurar CORS no hace privado el ERP.

La restricción necesita una arquitectura de red/acceso que preserve:
- Acceso autorizado del personal.
- Comunicación del servidor de tienda con ERP.
- Procesamiento de callbacks mediante una entrada pública acotada.

## 6. Arquitectura propuesta

Comprador:
Vue + Storefront UI + SDK de Supabase.

Servidor público de tienda:
Un backend TypeScript pequeño con operaciones comerciales explícitas.

ERP privado:
ERPNext + grupo_real_tools.

Flujo:

Navegador
  ├─ Supabase Auth: correo y sesión
  └─ Backend público de tienda
       └─ Conexión privada autenticada a ERPNext

El backend público:
- Verifica el token de Supabase.
- Valida issuer, audience, expiración y firma.
- Rechaza identidades anónimas o no verificadas.
- Construye un contexto de identidad confiable.
- Expone únicamente endpoints permitidos.
- Mantiene las credenciales ERP exclusivamente en servidor.
- Filtra errores y respuestas.
- Sirve o redirige de manera segura los recursos públicos y documentos
  autorizados.

No convertirlo en un proxy genérico hacia métodos o recursos de Frappe.

Puede usarse frappe-js-sdk en el cliente ERP del servidor si simplifica el
trabajo. Su funcionalidad de login de Frappe no es la autenticación de los
compradores.

La ubicación exacta del backend TypeScript y su origen público están
pendientes de confirmar.

El repositorio tenía un workflow de Azure Static Web Apps sin API declarada.
Eso no demuestra por sí solo dónde está desplegado actualmente.

No presentar el proxy de desarrollo de Vite como backend de producción.

## 9. Modelo de comprador: propuesta mínima

Antes de crear un nuevo DocType Store Buyer, evaluar reutilizar Contact.

Contact ya aporta:
- Nombre.
- Correos.
- Teléfonos.
- Vínculos dinámicos con Customer.

Customer aporta la relación comercial.
Supabase conserva la identidad de autenticación.

Propuesta:
- Extender Contact con el identificador externo de Supabase.
- Validar el issuer/proyecto esperado desde configuración confiable.
- Agregar un campo específico de acceso habilitado a la tienda si se adopta
  este modelo.
- Relacionar Contact con el Customer autorizado.

Contact.status no representa habilitación de una cuenta de tienda.

Contact.user:
- Es opcional.
- Puede vincularse automáticamente con un User existente por coincidencia
  de correo.
- No debe usarse para autenticar ni autorizar al comprador.

Nunca invocar Contact.invite_user desde este flujo: puede crear User.

Reglas de identidad:
- No asociar o fusionar clientes automáticamente solo porque coincide el
  correo.
- No confiar en un Customer enviado por el navegador.
- Usar identidad verificada y un vínculo controlado.
- En la propuesta inicial, una identidad Supabase por Contact.
- El vínculo de identidad no se cambia salvo migración revisada.
- Fusionar, eliminar, renombrar o reasignar contactos no debe transferir
  silenciosamente acceso histórico a pedidos.
- Si existen varios contactos para un Customer, filtrar únicamente por
  Customer puede exponer compras ajenas.
- Si un Contact tiene varios vínculos a Customer, no elegir el primero
  arbitrariamente.

Si Contact no expresa de manera segura el ciclo necesario, documentar ese
gap y evaluar una tabla de asociación específica.

El modelo definitivo, sus campos y permisos necesitan revisión mediante
la UI de Frappe antes de implementarse.

## 14. Flujo de checkout

### Preparación

El navegador envía:
- SKU real de la variante.
- Cantidad.
- Dirección propia o campos permitidos de una dirección nueva.
- Opción de entrega.
- Opción de pago.

El servidor decide:
- Customer.
- Company.
- Warehouse.
- Price List.
- Precios.
- Descuentos.
- Impuestos.
- Conversión monetaria.
- Envío.
- Totales.

Respuesta propuesta:
- quote_id opaco.
- version.
- expires_at.
- currency.
- Líneas y cantidades.
- Subtotal.
- Descuentos.
- Impuestos.
- Envío.
- Total.
- Opciones y mensajes de disponibilidad.

Usar precisión de ERP y valores decimales de transporte adecuados.
No confiar en sumas de punto flotante del navegador.

### Confirmación

Solicitar:
- quote_id.
- version.
- Total/moneda aceptados como guardia de comparación, no como insumo de precio.
- Idempotency-Key.

Dentro de una operación coherente:
1. Autenticar y resolver al comprador.
2. Resolver la cotización propia y operación.
3. Si la operación ya terminó con el mismo payload, devolver su resultado
   antes de volver a evaluar vencimiento o precios.
4. Para una operación nueva, bloquear/verificar el consumo del checkout.
5. Revalidar estado, versión, totales y disponibilidad.
6. Si algo cambió, devolver nueva cotización y exigir confirmación del comprador.
7. Presentar Quotation mediante el ciclo nativo.
8. Mapear y crear/presentar Sales Order mediante entradas soportadas.
9. Guardar vínculo de resultado e idempotencia en la transacción ERP.
10. Confirmar antes de devolver éxito y de iniciar trabajo externo independiente.

Un checkout lógico puede producir como máximo un pedido completo.
Cambiar la idempotency key o la versión no debe crear otro pedido.

La misma clave con distinto payload debe generar conflicto.

El resultado de una respuesta perdida debe poder recuperarse aunque la
cotización ya haya vencido.

La persistencia de estas garantías requiere metadata/constraints aprobados.
No prometer que un diccionario en memoria resuelve idempotencia.

### Stock

Definir y probar:
- Momento de reserva.
- Momento de liberación.
- Expiración de pedidos pendientes.
- Cancelación.
- Dos compradores intentando comprar la última unidad.

No presentar la comprobación de cantidad en Vue como control suficiente.

## 15. Pagos

Métodos iniciales y pasarela siguen pendientes de decisión.

Reutilizar:
- Mode of Payment.
- Payment Gateway Account.
- Payment Request.
- Payment Entry.
- Integración de pasarela soportada, cuando exista.

La integración debe:
- Publicar solo métodos habilitados y aplicables.
- Mantener pagos manuales pendientes hasta su confirmación autorizada.
- Procesar callbacks firmados o verificados según el proveedor.
- Evitar duplicación por evento y por identidad semántica de pago/captura.
- Representar correctamente pagos parciales.
- Recuperarse de timeouts y respuestas perdidas.
- No marcar pagado porque el navegador volvió a una pantalla de éxito.

Mantener separado el pedido de la iniciación de pago.

Inspeccionar la transacción nativa del proveedor: Payment Request puede
llamar al controlador externo durante su presentación.
No crear overrides para satisfacer una abstracción ideal sin comprobar
cómo funciona la integración soportada.

Los callbacks públicos llegan al backend de tienda.
No deben depender de que el proveedor pueda entrar al ERP privado.

## 22. Pruebas de aceptación mínimas

Autenticación:
- Código válido permite entrar.
- Código incorrecto, vencido o ya usado falla.
- Límites de solicitudes/intentos funcionan.
- Renovación y logout respetan la semántica del proveedor.
- Tokens de otro issuer, vencidos o falsificados son rechazados.

Usuarios:
- Registro, login y checkout no crean compradores en User del ERP.
- No se invocan invitaciones de Contact.

Permisos:
- Comprador A no puede ver, modificar, pagar o descargar documentos de B.
- Cambiar IDs, correo, Customer o metadata del navegador no altera ownership.
- Contactos compartidos/múltiples vínculos no conceden acceso implícito.

Catálogo:
- Variantes, filtros, tallas, colores y paginación conservan el comportamiento
  comercial aprobado.
- Ítems deshabilitados/no publicados no se filtran accidentalmente al público.
- No se crean Website Item como requisito.

Precios:
- Manipular el navegador no modifica precios, impuestos, descuentos, moneda
  ni envío.
- Cotización cambiada requiere confirmación nueva.

Pedidos:
- Reintentos con la misma clave no duplican.
- Claves diferentes para el mismo checkout tampoco duplican.
- Replays después de vencimiento recuperan pedidos ya creados.
- Competencia por última unidad respeta la política aprobada.

Pagos:
- Eventos repetidos no duplican cobros/asientos.
- Eventos diferentes de la misma captura tampoco duplican.
- Parciales, fallos y abandonos se representan correctamente.
- El navegador no puede marcar pagado.

Privacidad ERP:
- El navegador no depende de endpoints ERP.
- Imágenes, PDFs, enlaces y callbacks siguen la arquitectura pública aprobada.
- El acceso no autorizado al origen ERP está restringido.
- El acceso del personal continúa funcionando.

Comunicaciones:
- Destinatario correcto.
- Eventos de tienda, sin ventas internas ajenas.
- Sin duplicados por reglas superpuestas.
- Sin enlaces al ERP para compradores.

Infraestructura:
- Restore real probado con alcance autorizado.
- Jobs/integraciones aislados en staging.
- Backups y claves necesarios preservados.
- Replicación medida, no asumida.
- Mantenimiento del bench probado contra el comportamiento acordado de tienda.
- Rollback y operaciones en vuelo contemplados.
